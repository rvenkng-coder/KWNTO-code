# Findings: Accounts and teams

Record anything unexpected here: PocketBase behaviour that differs from what the plan assumed, and what was done about it.

## Task 1

- **Migrations are not isolated like hooks.** In PocketBase 0.40.6 a migration file's top-level `const` and `function` are visible inside its `migrate()` callbacks (`1794360000_system_settings.js` uses a `TABLES` list and a `count()` helper; the rule tests pass). The isolated-scope rule of the router applies to hook handlers only.
- **Settings numbers are not `required`.** A required `number` field rejects `0` in PocketBase (zero is "blank"), and 0 is a legitimate value for some settings. They are `onlyInt` with `min: 0` instead; the row always exists, and `lib/settings.js` throws if it does not.
- **`lib/*.js` needs a CommonJS marker for Vitest.** The root `package.json` has `"type": "module"`, so Node loads `backend/pb_hooks/lib/*.js` as ES modules and `module.exports` fails (`ReferenceError: module is not defined in ES module scope`). Added `backend/pb_hooks/package.json` with `{"type": "commonjs"}`; the plan's `.js` file names stay. PocketBase ignores the file (it loads only `*.pb.js`); rule tests and a probe confirm hooks still load.
- **Probe of the hook runtime (throwaway container, temporary route).** Inside PocketBase 0.40.6: `getSystemAccess` and `getSystemBehavior` return the documented shapes with the defaults; `logEvent` writes an entry, and with an invalid type it prints `security log: could not record a "not-a-type" event: GoError: type: Invalid value not-a-type.` and does not throw; `require(`${__hooks}/lib/...`)` and the global `Record` work from a required module; with `security_retention_days = 0`, `POST /api/crons/purge_security_events` (204) removed every entry.
- **No automated purge test yet.** It would need `security_retention_days` changed during a run, but rule files still run in parallel and `system_behavior.rules.test.ts` asserts the default 365, so it would be flaky. The rule test pins that the job is registered (`0 3 * * *`); the purge itself was checked by the probe above. Once Task 3 sets `fileParallelism: false`, an end-to-end purge test can be added safely.

## Task 2

- **`@request.body.user:isset = false` works in 0.40.6** as the guard on `user_preferences.updateRule`: a user's update that sends `user` (even their own id) is refused and the row keeps its owner. A mutation run without the guard makes the "cannot change which account" rule test fail, so the test pins it.
- **`quota_override_bytes` cannot be "empty" separately from 0.** A PocketBase number field stores an unset value as `0`, so `0` means "use `system_storage.default_quota_bytes`" (documented in `docs/admin/settings.md`). Consequence: the admin cannot give one user a 0-byte quota through this field. If that is ever needed it takes a separate field (for example a `quota_override_set` bool); not built (YAGNI).
- **`onRecordAfterCreateSuccess` on `users` runs before the create response is sent**, so the rows exist by the time the caller gets the new account (the rule tests read them straight after `createUser()`). It runs after the account is saved, so the hook catches and logs a failure instead of failing the sign-up; Task 4's `ensureUserRecords` at sign-in repairs it. It is a model hook, so it fires for dashboard and server-side creates as well as API sign-ups.
- **The migration repeats the defaults** instead of requiring `pb_hooks/lib/user-records.js`: a migration is a snapshot and must not change behaviour when the helper does later.
- **Backfill probed** (throwaway container, bind-mounted scratch data folder, no Docker volume): a user created under migrations up to 1794360100 got exactly one row in each table, with the defaults, after a restart with 1794360200. Rule tests cannot cover this because the test backend starts with no users.
- **Rule-test mutation check:** with `user_limits`/`user_status` list, view and update set to `user = @request.auth.id`, and the `isset` guard removed, 5 rule tests fail (the owner and other-user checks of both tables and the change-owner test of `user_preferences`).

## Task 3

- **Hook names in 0.40.6** (from the generated `pb_data/types.d.ts` and the v0.40.6 source, `apis/record_auth_*_confirm.go`): `onRecordConfirmVerificationRequest` and `onRecordConfirmPasswordResetRequest`. There is no `onRecordAfterConfirmVerificationRequest`; "after" work goes after `e.next()` in the same handler.
- **`verified: true` from a visitor is already refused by PocketBase 0.40.6**: without the hook, a public create with `verified: true` answers 400 `{"verified": {"code": "validation_values_mismatch"}}` (only superusers and managers may set it; `users.manageRule` is null). The hook sets `verified` to false before `e.next()`, so with it the request succeeds and the account is stored unverified. The rule test accepts either outcome and checks the stored value, so it does **not** fail if only the hook line is removed (PocketBase's own check still protects); it fails if both protections go.
- **Response timing.** In the create, update and confirm handlers the response is written inside `e.next()` (after the save). The `signup` event is logged after `e.next()` in `onRecordCreateRequest` rather than in `onRecordAfterCreateSuccess` as the task file said: the request hook has the caller's IP (`e.realIP()`) and knows whether the caller is the admin, so admin-created accounts are not logged as sign-ups. Go buffers the small JSON response until the handler returns, so the log row exists by the time the client reads the response; the rule tests read it straight away and passed on every run.
- **The reset confirm sets the password inside `e.next()`**, so the hook reads the new password from the request body. The reset form also validates length against the password field's `min` before the hook runs, so with the 1794360300 migration (`min` 10) a too-short reset is refused by PocketBase itself (`validation_length_out_of_range`), and the hook adds letter, number and common-password checks.
- **`ApiError` data must hold `ValidationError` values.** A plain `{ code, message }` object is turned into `validation_invalid_value` for each key; `new ValidationError(code, message)` gives `{"password": {"code": "validation_password_rules", "message": ...}}`.
- **`\p{L}` and `\p{N}` work in the PocketBase JS runtime** (probe: `contraseña12` and a Japanese passphrase with a digit were accepted at sign-up).
- **Password rules apply to the admin too.** The plan exempts the admin only from the registration switch and the verified flag; an admin `PATCH` with `password: short1` is refused with the rule message (probe). Admin-created accounts (`createUser()`) skip the closed-registration check (rule test).
- **`emailVisibility` is forced private by the hook (review fix).** It is a per-record flag (default false), not a collection setting, so the migration does not touch it. Task 3 first relied on the users list and view rules (own record only), but Task 6 lets teammates see each other's user records, so the hook now enforces it: at sign-up a non-superuser's `emailVisibility` is set to false (like `verified`); on update, a non-superuser who sends `emailVisibility` has it **reset to false** (chosen over a 400 so a form that sends the flag with a name change still saves the name). The admin can still set it. Two rule tests pin this, one per line (mutation: each removed line fails its own test).
- **Probe of verification and reset (throwaway container, a temporary route mounted from the scratchpad that minted tokens with `newVerificationToken()` and `newPasswordResetToken()`; not committed):** confirm-verification 204 and one `verification` event; a second confirm 204 and no second event; reset with `short1`, `Password123`, `abcdefghijk` all 400; a good reset 204, one `reset` event, and the new password signs in. All events carry the user and IP. These two paths have no automated test (the tokens come by mail); Task 5's runbook walk checks reset by hand.
- **Purge test (carry-over from Task 1).** `security_events.purge.rules.test.ts` runs the job through `POST /api/crons/{id}` (SDK `admin.crons.run`). The API cannot backdate an entry (`created` in a create or update body is ignored, probed), and retention is whole days, so the test moves the cut-off: with 365 days a fresh entry stays; with 0 days the same entry is older than the cut-off and is removed. Mutation checks: a job that deletes nothing fails it, and a job that ignores the setting (always 0 days) fails it. Safe only because rule files now run one at a time (`fileParallelism: false`).
- **Mutation check of the sign-up hook:** with `users-signup.pb.js` removed, 4 tests fail (rule messages on sign-up and change, closed registration, signup event).

## Task 4

- **Probe of the sign-in events (throwaway container `kwnto-probe4` on 8095, scratch copy of `pb_hooks` plus a logging hook; not committed).** In 0.40.6 `RecordAuthWithPasswordRequestEvent` has `identity` (the raw string as typed, **not** trimmed or lower-cased), `identityField` (empty unless the client sends one), `password` and `record` (null when no account matches); `e.realIP()` exists. `RecordAuthRequestEvent` has `record`, `token`, `meta` and `authMethod` but **no identity**.
- **The success path runs inside the password hook's `e.next()`.** PocketBase checks the password inside `e.next()`; on success it calls `RecordAuthResponse`, which triggers `onRecordAuthRequest` (still inside that `e.next()`) before writing the token response. So an error thrown in `onRecordAuthRequest` (the block) surfaces from the password hook's `e.next()` like a wrong password does. Both are a `GoError` with `value.status` (400 "Failed to authenticate." or our 403). The hook therefore counts a `failure` only for PocketBase's wrong-credentials answer (`error.value.status === 400`, the same for an unknown email), not on every error; a rule test pins that a blocked user's right-password attempts are not failures, and another set fails if nothing is counted. Checking the password again (`e.record.validatePassword`) was tried first and dropped: it adds a second bcrypt only for real accounts, widening the response-time gap between real and unknown emails.
- **`onRecordAuthRequest` also runs for `auth-refresh`** (`authMethod` is `""` there; `"password"` for a sign-in). Consequences: the block check (in that hook) also refuses a blocked account's token refresh, which is wanted; and the `sign-in` event is written in the password hook after `e.next()` instead of in `onRecordAuthRequest` as the task file said, so refreshes do not log sign-ins (and silently reset the lockout count) and the event has the email as typed. `ensureUserRecords` and the status read stay in `onRecordAuthRequest`, so they also run on refresh (two or three small queries).
- **The email lookup is case-sensitive and untrimmed in 0.40.6**: `Good@Example.test` and ` good@example.test ` do not find `good@example.test` even with the right password (400). The lockout key is lower-cased and trimmed anyway, so varying the case cannot start a fresh count; such attempts count against the real address's pair.
- **`e.realIP()` ignores `X-Forwarded-For` by default** (probe: a forged header still gave `172.17.0.1`, the Docker gateway), because `Settings.trustedProxy` is empty. Good: a client cannot fake its IP to dodge the lockout. Behind the deployment's reverse proxy the trusted header must be configured, or every request has the proxy's IP and the per-pair lockout becomes per-account (documented in docs/security.md section 3 for the deployment plan).
- **JSON-path filters work on `security_events.detail`**: `detail.identity = {:id}` in `findRecordsByFilter` matched only the right rows (probe). `record.getDateTime("created").time().unixMilli()` gives ms. A `created > {:since}` filter compares text, so the bound is passed in PocketBase's stored format (`YYYY-MM-DD HH:mm:ss.SSSZ`, the ISO `T` replaced by a space), as `lib/retention.js` does.
- **PocketBase sentenizes `ApiError` messages**: `new ApiError(403, "blocked test")` answers `"Blocked test."` (capital first letter, full stop added when there is no closing punctuation). So the block refusal reads `Your account is blocked: Spamming.` and a lockdown message `Maintenance` reads `Maintenance.`; the rule tests expect those exact texts. The lockout and default lockdown texts already end in a full stop and are unchanged.
- **Settings of 0:** `max_failed_logins` and `lockout_minutes` allow 0 (Task 1). `decideLockout` treats 0 for either as "lockout off" (a limit of 0 would refuse every first attempt; 0 minutes is an empty window). Unit tested and documented in docs/admin/settings.md.
- **`ensureUserRecords` race (review carry-over):** when a create fails, it re-checks and rethrows only if the row is still missing. A unit test fakes the unique-index failure with and without a competing row. A still-missing `user_status` after the repair refuses the sign-in with 500 (fail closed); that branch has no rule test, because the repair always recreates the row in a healthy backend.
- **What the rule tests cannot show:** every request comes from one IP, so the per-IP part of the lockout is pinned only by the `decideLockout` unit tests (which receive one pair's failures) and the hook's `ip = {:ip}` filter. A mutation that drops the IP from the filter passes the rule tests.
- **Not covered by the lockout:** OTP and OAuth2 sign-ins (both off in the `users` collection) would skip the lockdown and the lockout, which are in the password hook; the block would still apply. If either is ever turned on, the hooks need extending. Lockdown and block refusals are not logged (the D4 type list has no value for them).
- **Parallel guesses pass the lockout (review finding, documented, not fixed).** The failure count is read before `e.next()` and a failure is written after the bcrypt check, so simultaneous attempts are all checked against the same count. Probe on the test container (one account, 20 wrong attempts sent at once with curl, 16 CPUs): 18 × 400 and 18 `failure` entries, 2 × 429. Controller ruling: no serialised counter and no limiter change in Task 4 (enabling it globally would affect every rule test); documented in docs/security.md section 3 and the roadmap's Deployment line.
- **Built-in rate limiter in 0.40.6:** `GET /api/settings` → `rateLimits` = `{enabled: false, excludedIPs: [], rules: [*:auth 2 per 3 s, *:create 20 per 5 s, /api/batch 3 per 1 s, /api/ 300 per 10 s]}` (audience `""`, both guests and signed-in). Labels may be tags (`users:auth`, `*:auth`), paths or path prefixes. Dashboard: Settings, Application, Rate limiting. Probe: after `PATCH /api/settings {"rateLimits":{"enabled":true}}` on the throwaway test container, the same 20 parallel attempts gave 2 × 400 (2 `failure` entries) and 18 × 429 (PocketBase's own limiter answer). The limiter counts per IP, so the trusted-proxy note above applies to it too.
- **Rule-test mutation check** (scratchpad script, each mutation rebuilt and run against `users.signin.rules.test.ts`): no lockdown check fails 2 tests; no lockout fails 4; counting every error as a failure fails 1; counting no error fails 5; no reset by a sign-in fails 1; logging `lockout` as `failure` fails 1; identity not normalised fails 1; no block fails 2; no repair fails 1; no `sign-in` event fails 2.

## Task 5

- **Probe of the session mechanisms (step 1; throwaway container `kwnto-probe5` on 8095, scratch `pb_data` bind mount, scratch copy of `pb_hooks` plus a temporary probe file with two superuser-only routes and a logging `onRecordAuthRefreshRequest`; removed afterwards, not committed).** Output, with users A and B signed in afresh before each step:

  ```
  before: A refresh 200, B refresh 200
  (a) rotate-user A: {"before":"CHEQ8Y0O...","after":"vWa9vDYh..."}   (record.refreshTokenKey(); app.save(record))
  (a) after: A refresh 401, B refresh 200
  (b) rotate-all: {"beforeLen":50,"changed":true}   (collection.authToken.secret = $security.randomString(50); app.save(collection))
  (b) after: A refresh 401, B refresh 401, admin refresh 200
  (b) A signs in again: token length 224, refresh 200
  PROBE onRecordAuthRefreshRequest ran for <id>   (4 times: once per refresh that answered 200)
  ```

  So (a) `record.refreshTokenKey()` plus a save ends that user's tokens at once and no one else's; (b) a new `users.authToken.secret` ends every user token at once while the admin's superuser token keeps working (it is signed with the `_superusers` secret), and people can sign in again straight away; (c) `auth-refresh` runs `onRecordAuthRefreshRequest`, but only for a token that is still valid: an ended token is refused with 401 before any hook runs. Saving the collection from a route did not write a migration file (the image runs `serve` without automigrate).
- **No new `onRecordAuthRefreshRequest` hook.** Task 4's `onRecordAuthRequest` already runs on `auth-refresh` and refuses a blocked account with "Your account is blocked: <reason>." (403). A second hook would duplicate it. With Task 5 a block also renews the token key, so in practice the old token gets 401 before the Task 4 check is reached; the 403 refusal remains the guard if a token ever survives a block. Rule test 4 accepts 401 or 403 for the refresh (as the brief says) and also checks that the old token can no longer read the user's own record: a refused refresh alone does not end a session (before Task 5, the RED run showed the blocked user's token still read their record with 200).
- **Hook kind: `onRecordUpdate`, not `onRecordAfterUpdateSuccess`** (the task file named the latter) for the block and the settings log. `onRecordUpdate` wraps the save, so the handler reads `e.record.original()` (the stored values) before `e.next()` and compares after it, and an error thrown after `e.next()` reaches the caller. For a block that matters: the status is saved first (from then on sign-ins and refreshes are refused), then the token key is renewed; if that fails, the request answers 500 "The account is blocked, but its sessions could not be ended. Sign it out with the sign-out route." rather than a success. A block only counts when `blocked` goes from false to true, so changing a blocked account's reason does not log a second block (pinned by test 6).
- **A block writes two `admin` entries:** `block` (with the reason) and a `settings` entry for `user_status` listing `blocked` (and any other changed fields). The hook does not fill `blocked_at`; the admin may set it in the dashboard (runbook).
- **Settings tables have no `created` or `updated` fields**, so the change list never contains them; an `autodate` skip was written first and removed because no test could reach it (its mutation survived). Values are logged as plain JSON (`getFloat`, `getBool`, parsed `json`, otherwise text), because `record.get()` returns Go values (a json field is raw bytes).
- **Unknown id:** the sign-out route answers 404 "No account with this id." Without the route, PocketBase also answers 404 ("The requested resource wasn't found."), so the test checks the message too.
- **Rule-test mutation check** (scratchpad script, each mutation rebuilt and run against `admin-controls.rules.test.ts`): no token-key refresh in sign-out fails test 1; secret unchanged in sign-out-all fails test 2; routes without `requireSuperuserAuth` or with `requireAuth` fail test 3; unknown id answering 204 fails test 5; no token-key refresh on block fails test 4; block not logged, or every save counted as a block, fails test 6; settings not logged, or `user_status` left out, fails test 7.

## Task 6

- **A record create is not a transaction in 0.40.6 (read in the v0.40.6 source, then probed).** `apis/record_crud.go` `recordCreate` calls `form.Submit()`, which is a plain `app.SaveWithContext`; `core/db.go` `create()` runs `OnModelCreate` → validation → `OnModelCreateExecute` → insert with no transaction of its own, then fires `OnModelAfterCreateSuccess` straight away (or, only when the app is already a transaction app, after the commit). So the plan's `onRecordAfterCreateSuccess` runs after the team is stored and outside any transaction.
- **Design used instead: the `onRecordCreate` model hook opens the transaction and moves the team's own insert into it** (`e.app.runInTransaction((txApp) => { e.app = txApp; e.next(); save owner row; save settings row })`). Assigning `e.app` works from the JS runtime (the rule tests pass through it). Any error rolls back the team too, so the plan's "delete the team if it fails" step is not needed. It is a model hook, so dashboard and server-side creates get the rows as well.
- **Forced-failure probe (throwaway containers on 127.0.0.1:8095, tmpfs data, scratch copy of `pb_hooks` with one inserted line that throws for a team named `PROBE-FAIL`; not committed):**
  - (a) Task 6's design, throw after the owner row is saved and before the settings row: `create PROBE-OK: 200`, `create PROBE-FAIL: 400 "Failed to create record."`; the admin then sees teams `['PROBE-OK']` only, 1 `team_members` row and 1 `team_settings` row (both of PROBE-OK). Nothing of the failed team is left.
  - (b) The plan's design (`onRecordAfterCreateSuccess` with `runInTransaction`, no compensating delete), same throw: the caller also gets 400, but the admin sees teams `['PROBE-OK', 'PROBE-FAIL']`: PROBE-FAIL is stored with no members, invisible even to its owner. This is why (a) was chosen.
  - No automated test of the failure path: provoking a failure from a rule test would need a test-only trigger in production code. The probe is the evidence.
- **A failed create rule answers 400, not 403** (`recordCreate`: `e.BadRequestError("Failed to create record", "create rule failure")`; the rule is checked before any request hook runs, so a hook cannot turn it into 403). The brief expected 403 for an unverified user; the test asserts 400 and that no team exists, and a mutation that drops `@request.auth.verified = true` makes it fail. A locked (`null`) create rule still answers 403.
- **`?=` with a back-relation is the membership check:** `team_members_via_team.user ?= @request.auth.id` (teams) and `team.team_members_via_team.user ?= @request.auth.id` (team_members). Mutation with `=` instead of `?=`: 3 teams tests fail (a member of a two-member team no longer sees it), so `=` means "every row matches" here.
- **Additions to the plan's rules (sensible, tested):** `teams.updateRule` also has `@request.body.owner:isset = false`. Without it the owner could hand the team to any account (an outsider would get owner powers without a membership row, the `role` column would be wrong, and the new "owner" could no longer delete their account). `team_settings.join_code` has a unique index (joining looks a team up by its code; the hook picks a code no team has, up to 5 tries). `team_members.user_name` is set by an `onRecordCreate` hook on `team_members` from `users.name`, whatever the caller sent, so every way of adding a member (admin, Task 7 join, Task 8 invite) gets the name without repeating the code.
- **A member's own email can appear in a team response when they expand their own user** (`expand: 'user'` on their own membership row): the users rule shows each person their own record. The first version of the member-list test asserted no `@` at all with that expand and failed for this reason only (probe output: the only email was the caller's own). Per Review Focus 5 ("never contain another person's email") the test now asserts no `@` at all without expand and for the owner's row expanded, and none of the other person's email in the expanded list. Not hidden in code: it is the caller's own data, readable from `/users` anyway. Flagged for the reviewer.

## Task 7

- **Order of checks in `POST /api/kwnto/teams/join`:** `$apis.requireAuth("users")` (401) → `e.auth.verified()` (403 "Verify your email address first.") → the attempt limit (429) → the code lookup (404) → the membership. Signed-out and unverified calls are refused before anything is counted or logged: a signed-out caller has no account to count against, and an unverified one cannot join anything.
- **Refused-by-limit attempts are logged with `detail.limited: true` and not counted** (a choice the brief left open, made for the same reason as the lockout's `lockout` type: hammering must not extend the limit, which then ends an hour after the attempts that caused it). The count filter is `user = {:user} && (type = 'join' || type = 'invite') && created > {:since} && detail.limited != true`. In 0.40.6 `detail.limited != true` keeps rows whose `detail` has no `limited` key (the rule tests count plain `join` rows and a seeded `invite` row with `detail: { ok: true }`), and drops the limited ones (raising the setting from 3 to 4 after two 429s lets exactly one more attempt through). **Task 8 must mark its own limit refusals the same way** (`invite` with `detail.limited: true`), or refused invites will extend the shared limit.
