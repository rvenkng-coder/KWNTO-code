# Backend developer guide

The backend is PocketBase, run in Docker. The image is `kwnto-pocketbase:dev`, built from [backend/Dockerfile](../../backend/Dockerfile).

## Start the dev backend

1. Copy `.env.example` to `.env` and set `KWNTO_ADMIN_EMAIL` and `KWNTO_ADMIN_PASSWORD` (10 or more characters). There is no default password: without both values the container refuses to start (exit code 64).
2. Run `npm run dev:backend`.
3. The API is at `http://127.0.0.1:8090/api/` and the dashboard at `http://127.0.0.1:8090/_/`. Sign in with the admin email and password from `.env`.

Data lives in the Docker volume `kwnto-dev-data`. `backend/pb_migrations` and `backend/pb_hooks` are bind-mounted, so edits apply without a rebuild (restart the container to run a new migration).

## How the admin is created

The migration [1794355200_initial_superuser.js](../../backend/pb_migrations/1794355200_initial_superuser.js) creates one superuser from `KWNTO_ADMIN_EMAIL` and `KWNTO_ADMIN_PASSWORD`. PocketBase runs each migration once per data folder, so a restart with different values never overwrites a password changed in the dashboard. A test pins this. Never edit that migration after it has run; add a new one instead.

To reset a lost password, use `docker compose -f compose.dev.yaml exec pocketbase /pb/pocketbase superuser upsert EMAIL PASSWORD --dir=/pb/pb_data`.

## Hooks and their helpers

Behaviour that access rules cannot express lives in JavaScript hooks in `backend/pb_hooks/`. PocketBase loads every `*.pb.js` file there; files in `lib/` are only loaded when a hook requires them.

| Path | What goes there |
|---|---|
| `backend/pb_hooks/*.pb.js` | Thin hooks, routes and scheduled jobs, for example [retention.pb.js](../../backend/pb_hooks/retention.pb.js) (the daily `purge_security_events` job), [users-defaults.pb.js](../../backend/pb_hooks/users-defaults.pb.js) (gives each new account its per-user rows), [users-signup.pb.js](../../backend/pb_hooks/users-signup.pb.js) (closed registration, the verified flag at sign-up, the password rules on sign-up, change and reset, and the `signup`, `verification` and `reset` log entries) [users-signin.pb.js](../../backend/pb_hooks/users-signin.pb.js) (lockdown, lockout, block and the `sign-in`, `failure` and `lockout` log entries) and [admin-controls.pb.js](../../backend/pb_hooks/admin-controls.pb.js) (the admin's sign-out routes, ending a blocked account's sessions, and the `admin` log entries for those and for settings changes) and [teams.pb.js](../../backend/pb_hooks/teams.pb.js) (a new team's owner row and settings row, in one transaction with the team; the `team_members.user_name` copy) and [teams-join.pb.js](../../backend/pb_hooks/teams-join.pb.js) (the join-by-code and regenerate-code routes, the attempt limit and the `join` log entries) and [teams-invites.pb.js](../../backend/pb_hooks/teams-invites.pb.js) (the invite, accept and decline routes, the `team_invites` name copies and the `invite` log entries) and [content-guard.pb.js](../../backend/pb_hooks/content-guard.pb.js) (the guarded update of every content collection, see "Guarded writes" below) and [projects.pb.js](../../backend/pb_hooks/projects.pb.js) (a new project's settings row and `Chapter 1`, in one transaction with the project; the first node of a project becomes its `start_node`, see "References stay in their project" below). |
| `backend/pb_hooks/lib/*.js` | Shared helpers: [settings.js](../../backend/pb_hooks/lib/settings.js) reads the system settings, [security-log.js](../../backend/pb_hooks/lib/security-log.js) writes the security log, [retention.js](../../backend/pb_hooks/lib/retention.js) computes purge cut-offs, [user-records.js](../../backend/pb_hooks/lib/user-records.js) creates an account's missing per-user rows (`ensureUserRecords`), [password-rules.js](../../backend/pb_hooks/lib/password-rules.js) checks a new password (`checkPassword`) against the list in [common-passwords.js](../../backend/pb_hooks/lib/common-passwords.js), [lockout.js](../../backend/pb_hooks/lib/lockout.js) decides whether an account and IP pair is locked out (`decideLockout`), [join-code.js](../../backend/pb_hooks/lib/join-code.js) makes a team join code (`generateJoinCode`), [unused-join-code.js](../../backend/pb_hooks/lib/unused-join-code.js) picks one no team has yet with crypto-quality randomness (`unusedJoinCode`, used by team creation and regeneration), [rate-limit.js](../../backend/pb_hooks/lib/rate-limit.js) decides whether a user has used up their attempts (`isOverLimit`), [team-attempts.js](../../backend/pb_hooks/lib/team-attempts.js) counts a user's join and invite attempts from the security log and applies it (`teamAttemptLimitReached`, shared by both routes so they count alike), [invite-email.js](../../backend/pb_hooks/lib/invite-email.js) cleans a typed email, takes its domain for the log and keeps an exact-address safeguard from the time accounts could differ only in case (`typedEmail`, `normalisedEmail`, `emailDomain`, `chooseAccountIndex`), [team-invites.js](../../backend/pb_hooks/lib/team-invites.js) holds the invite routes' reads and writes (email lookup, creating an invite, answering one in a transaction with the member row), [content-guard.js](../../backend/pb_hooks/lib/content-guard.js) holds the guard's pure parts (`GUARDED`, `guardedTable`, `changedFields`, `parseSentVersion`). |

Rules for this code:

- **Hook handlers run in isolated scopes.** A handler cannot see variables or functions declared outside it in the same file. Load shared code inside the handler: `const { getSystemBehavior } = require(`${__hooks}/lib/settings.js`)`. (Migrations are different: a migration's top-level helpers are visible inside `migrate()`.)
- **`lib/` is CommonJS** (`module.exports`), so the same file runs in PocketBase and in Vitest. [backend/pb_hooks/package.json](../../backend/pb_hooks/package.json) says `"type": "commonjs"` because the project root is an ES module package; without it, Node refuses `module.exports` in these files.
- **Keep decisions pure and test them** in `tests/hooks/<name>.unit.test.ts` (part of `npm run test:unit`). Tests load a helper with `createRequire(import.meta.url)`. Where a helper needs a PocketBase global such as `Record`, the test provides a small fake (see `tests/hooks/security-log.unit.test.ts`).
- Settings are read at run time with `getSystemAccess($app)` and `getSystemBehavior($app)`, never copied into code. They throw if a settings record is missing, because that is a broken install. The tables and their defaults are described in [docs/admin/settings.md](../admin/settings.md).
- Write security events with `logEvent($app, type, userId, ip, detail)`. It never throws, so it is safe on a sign-in path. Inside a hook handler, pass the event's app (`logEvent(e.app, ...)`), not the global `$app`: the handler may run inside a transaction, and a write through `$app` would wait on the transaction's database lock until SQLite's busy timeout.
- **Looking an account up by email:** emails are case-insensitive (developer decision, 2026-11-13; final review I2). They are stored lower-case and trimmed (users-signup hook) and PocketBase's own unique email index is `COLLATE NOCASE` ([1794360700_users_email_collate_nocase.js](../../backend/pb_migrations/1794360700_users_email_collate_nocase.js)). That collation is what makes PocketBase's lookups (`findAuthRecordByEmail`, sign-in, password reset, verification) ignore case in 0.40.6: an index on `LOWER(email)` does not (a reset typed with a capital sent no mail). Only stray spaces are not ignored, so the sign-in hook looks an untrimmed address up again. Filters in hooks cannot say `COLLATE`; `email:lower = {:email}` works but scans the table (see `findUserByEmail` in [team-invites.js](../../backend/pb_hooks/lib/team-invites.js)).
- **A record create is not a transaction.** In PocketBase 0.40.6 the API saves a record without a transaction, and `onRecordAfterCreateSuccess` runs after the record is stored, so a failure there leaves the record behind. When related rows must exist together with a record (a team, its owner row and its settings row), do the work in the `onRecordCreate` model hook inside `e.app.runInTransaction((txApp) => { e.app = txApp; e.next(); ... })`: setting `e.app` moves the record's own insert into the transaction, and any error rolls back all of it (see [teams.pb.js](../../backend/pb_hooks/teams.pb.js)). **The cost: PocketBase then sends no realtime `create` event for that record.** Use the pattern only for collections nobody watches live (teams, projects). For a content record a teammate's open editor must see, call `e.next()` first and do the extra work in its own `e.app.runInTransaction(...)` after it, as the `nodes` hook in [projects.pb.js](../../backend/pb_hooks/projects.pb.js) does; `tests/rules/content-door.rules.test.ts` ("a teammate's new records arrive as create events") fails if a node's insert moves back into a transaction.

## Guarded writes

Every update of `projects`, `project_settings`, `chapters`, `nodes`, `script_lines`, `cues` and `connections` goes through one hook, [content-guard.pb.js](../../backend/pb_hooks/content-guard.pb.js) ([decision 0002](../decisions/0002-realtime-spike.md), option 2; editor core plan D3). It exists because plain PocketBase updates lost one of two concurrent edits of different fields in the real-time spike.

- **What the client sends:** a normal `PATCH /api/collections/<name>/records/<id>` with only the fields the person changed, plus `version`: the version of the record it last read. Each collection's update rule requires `version` in the body (`@request.body.version:isset = true`), so a PATCH without it is refused like any other rule failure (403 or 404). A `version` that is not a whole number from 0 is a 400 `version is required`. A create may not send `version` (it starts at 0) or `deleted_at`.
- **What the server does:** in one transaction it runs `UPDATE <table> SET version = version + 1 WHERE id = ? AND version = <sent>`. If no row changed, someone saved first: it answers **409** `{"message": "This record was changed by someone else. Reload it and try again."}` and nothing is written. Otherwise it reads the record again inside the transaction, copies onto it only the fields whose value differs from the stored one (`changedFields`; never `id`, `version`, `created` or `updated`), saves it and answers 200 with the saved record (`version` is the stored one plus 1).
- **What the client does on 409:** re-read the record, apply only its own fields again on top, and send with the new version. Bound it (the app gives up after 20 tries with `Could not save: too many people are editing this at once. Try again.`).
- **Why the hook is on the update request:** the spike measured that a version check in the model hooks (`onRecordUpdate`, `onRecordUpdateExecute`) loses edits, because those hooks run outside the save transaction: two saves read the same version, or a bump commits without its data. Only `onRecordUpdateRequest`, doing the bump and the write in one explicit transaction, kept every edit (100 of 100 rounds). The hook replaces PocketBase's own save, so it must never become a back door: in 0.40.6 the collection's update rule is checked **before** `onRecordUpdateRequest` runs, so the hook does not check access itself. `tests/rules/chapters.rules.test.ts` pins this (an outsider's update with the right version is refused), and `tests/rules/content-guard.rules.test.ts` pins the concurrency (20 rounds of parallel edits, both kept).
- **The table name** in the SQL comes from `guardedTable(e.record.collection().name)`, which throws for any name not in `GUARDED`; it never comes from the request.
- **Adding a collection to the guard:** add its name to `GUARDED` in [lib/content-guard.js](../../backend/pb_hooks/lib/content-guard.js) and to the tag list at the end of `content-guard.pb.js`; give it a `version` field (`number`, `onlyInt`, `min: 0`, not required, so 0 is valid); make its update rule require `@request.body.version:isset = true` and its create rule require `@request.body.version:isset = false`; add a rule test that an update without `version`, with a stale one, and by an outsider are all refused. Admins editing a record in the dashboard pass through the guard too (not yet tested): the dashboard form sends every field, `version` included, so a save there should work unless someone changed the record meanwhile, and is refused with the 409 message if they did.

## References stay in their project

Every content record carries `project`, set on create and never changed. The create rules of `nodes`, `script_lines`, `cues` and `connections` check each reference in the body against it with PocketBase's body-relation lookup, for example `@request.body.chapter.project = @request.body.project` (lines and cues: `node`; connections: both `from_node` and `to_node`). 0.40.6 resolves that form on create, so no hook is needed; `tests/rules/script_lines.rules.test.ts` fails if the check is dropped. The update rules refuse `project` and every reference field in the body (`@request.body.<name>:isset = false`), so a record never moves; `projects` updates accept `start_node` only when it is empty or `@request.body.start_node.project = id`.

**Start node** (editor core plan D7): an `onRecordCreate` hook on `nodes` in [projects.pb.js](../../backend/pb_hooks/projects.pb.js) opens a transaction, saves the node (`e.next()`), reads its project and, if `start_node` is empty, sets it to the new node and adds 1 to the project's `version`, so a project edit based on the old version gets a 409. Purging the start node empties the field (the relation does not cascade).

## Custom routes and the admin prefix

Custom routes live under `/api/kwnto/`. App routes so far: `POST /api/kwnto/teams/join` and `POST /api/kwnto/teams/{id}/regenerate-code` ([teams-join.pb.js](../../backend/pb_hooks/teams-join.pb.js)); `POST /api/kwnto/teams/{id}/invites`, `POST /api/kwnto/invites/{id}/accept` and `POST /api/kwnto/invites/{id}/decline` ([teams-invites.pb.js](../../backend/pb_hooks/teams-invites.pb.js)). What they answer is in [security.md section 3](../security.md#3-accounts-and-sign-in). They use `$apis.requireAuth("users")` (a signed-out caller gets 401) and check `e.auth.verified()` themselves (403). Inside a route, use `e.app` and pass every value from the request as a bound parameter (`{:name}`) in filters. Routes only the admin may call live under **`/api/kwnto/admin/`** (today: `POST /api/kwnto/admin/users/{id}/sign-out` and `POST /api/kwnto/admin/sign-out-all`, in [admin-controls.pb.js](../../backend/pb_hooks/admin-controls.pb.js); how to use them is the runbook in [security.md section 9](../security.md#9-if-you-suspect-a-compromise-the-incident-runbook)).

- Every admin route has the `$apis.requireSuperuserAuth()` middleware, so any other caller gets 401 or 403. Rule tests pin this (`tests/rules/admin-controls.rules.test.ts`).
- **The deployment plan must block `/api/kwnto/admin/` on the public address**, as it blocks the dashboard (`/_/`) and PocketBase's own admin API ([security.md section 6](../security.md#6-secrets-and-the-server)). The prefix exists so that one rule in the reverse proxy covers every admin route, present and future: the admin reaches them only through the private network, and a stolen admin password alone is not enough from the internet. Put every new admin-only route under this prefix, never elsewhere.

## Tests and the test backend

- `npm run test:container` builds the image and tests it with real containers (port `8093`, volume `kwnto-container-test`). It removes its own left-overs first, so it is safe to run again after a killed run.
- `docker compose -f compose.test.yaml up -d --build --wait` starts a throwaway backend on `127.0.0.1:8091` with the admin `admin@example.test` / `test-admin-password-1` and in-memory data. Stop it with `docker compose -f compose.test.yaml down -v`.

## Pinned version and how to bump it

PocketBase is pinned in `backend/Dockerfile` as build args `PB_VERSION` (currently `0.40.6`) and `PB_SHA256`. The image is verified with `sha256sum -c`, so the build fails if they disagree. To bump:

1. Choose the new version and read its release notes.
2. Copy the `pocketbase_<version>_linux_amd64.zip` line from that release's `checksums.txt`.
3. Change `PB_VERSION` and `PB_SHA256` together, then run `npm run test:container`.

The Alpine base image is pinned by digest in the same file.

## Password hashing

PocketBase v0.40.6 hashes passwords with **bcrypt, cost 10**. The password field type is documented as "storing bcrypt hashed strings" and hashes with `bcrypt.GenerateFromPassword(plain, cost)`, where an unset `Cost` falls back to `bcrypt.DefaultCost` ([core/field_password.go](https://github.com/pocketbase/pocketbase/blob/v0.40.6/core/field_password.go)). The default `_superusers` and auth `password` fields set no cost, and `bcrypt.DefaultCost` is 10 ([golang.org/x/crypto v0.58.0, bcrypt/bcrypt.go](https://github.com/golang/crypto/blob/v0.58.0/bcrypt/bcrypt.go)). bcrypt uses only the first 72 bytes of a password.

## The backend door (`frontend/src/backend/`)

The only place that imports `pocketbase`. Screens use `import { backend } from '../../backend'` and see only plain types from [types.ts](../../frontend/src/backend/types.ts) (`AuthUser`, `Team`, `TeamMember`, `TeamSettings`, `Invite`), never SDK records. `createBackend(baseUrl?)` in [client.ts](../../frontend/src/backend/client.ts) builds one with `auth`, `teams`, `preferences`, `projects` and `content`; `backend` in [index.ts](../../frontend/src/backend/index.ts) is the app's lazily created one. The SDK's request auto-cancel is off, because screens load twice in development (StrictMode) and a cancelled request would show as "cannot be reached".

- **`backend.auth`:** `signUp`, `signIn`, `signOut`, `current`, `refresh`, `requestVerification`, `requestPasswordReset`, `onChange`. `onChange(listener)` registers a listener that is called on **every** store change (sign-in, refresh, sign-out, another tab) with the mapped user or `null`; returns a function that removes only that listener; removing twice is harmless; a throwing listener does not stop others. `signIn` and `refresh` no longer call listeners directly—the SDK's `authStore.onChange` feeds them. `refresh()` re-reads the stored session (the `verified` flag changes after the email link); it ends the session only on 401, 403 or 404, and keeps it when the server cannot be reached. The app calls it on load and when the window gets focus.
- **`backend.teams`:** `list`, `create`, `remove`, `members`, `removeMember`, `settings` (owner only), `setJoinCodeEnabled`, `regenerateJoinCode`, `join`, `invite`, `invites` (pending only), `acceptInvite`, `declineInvite`. `create` sends the signed-in user as `owner` (the rule requires it) and refuses an unverified user before asking the server.
- **`backend.projects`:** `list(teamId)` (projects not in the trash, most recently updated first) and `create(teamId, name)` (the server adds the settings row and `Chapter 1`). Any member may do both.
- **`backend.content`:** the editor's only way to a project's content ([content.ts](../../frontend/src/backend/content.ts)). Types are in [content-types.ts](../../frontend/src/backend/content-types.ts): `Project`, `ProjectSettings`, `Chapter`, `StoryNode`, `ScriptLine`, `Cue`, `Connection`, each with `version`; `ContentRecords` maps a collection name (`ContentKind`) to its type, `EditableFields` lists what an update may change, and [content-mappers.ts](../../frontend/src/backend/content-mappers.ts) turns records into these types and back (`deleted_at` becomes `deleted`, an empty `start_node` becomes `null`).
  - `load(projectId)` returns `ProjectContent`: the project, its settings, and **every** chapter, node, line, cue and connection, **trashed ones included** (`deleted: true`); the editor store hides them.
  - `create(kind, record)` makes a chapter, node, line, cue or connection with the record's client-made `id`, never `version` or `deleted_at`. A create refused by the rules comes back as `forbidden` (PocketBase answers it with 400 and no field errors); a validation error stays `invalid` with `fields`.
  - `update(kind, id, changes, baseVersion)` sends only `changes` (trash with `{ deleted: true }`, which sets `deleted_at` to the browser's clock, plan D14; restore with `{ deleted: false }`) and the version the caller last saw. **It handles a 409 by itself** ([guarded.ts](../../frontend/src/backend/guarded.ts), see "Guarded writes"): it re-reads the record and sends the same changes with the fresh version, up to `MAX_SAVE_TRIES` (20) writes in all, then gives up with a `conflict` error whose message is `TOO_BUSY` (`Could not save: too many people are editing this at once. Try again.`). Any other error stops at once. It resolves to the saved record, with its new `version`.
  - `get(kind, id)` reads one record; a 404 (it does not exist, or the view rule hides it) gives `null`, any other error throws a `BackendError`. The sync engine uses it to check whether a remove or a create whose answer was lost already happened. A `create` with an id that exists rejects with kind `invalid` and `fields.id` set.
  - `update(..., baseVersion, { shouldRetry })`: the optional `shouldRetry(current)` is asked after each 409 with the freshly read record. When it returns `false` the retry stops at once with an `EditConflict` (kind `conflict`, status 409, message `EDIT_CONFLICT`, the record in `server`); the sync engine uses it for edits made offline (D3, D4). Without it nothing changes: edits made online are retried silently.
  - `remove(kind, id)` deletes a line, cue or connection outright (projects, chapters and nodes are trashed with `update`).
  - `subscribe(projectId, onEvent)` opens one live subscription per content collection, filtered by project (the `projects` collection: its one record), and resolves to a function that closes all seven. Each change arrives as a `RemoteEvent` (`kind`, `action` `create`, `update` or `delete`, and the mapped `record`), the caller's own saves included. PocketBase sends an event only to people its view rule lets see the record. **Events missed while disconnected are not replayed** (decision 0002, finding E). The optional third argument `onReconnect` is called each time the event stream connects again while the subscription is open (the SDK sends `PB_CONNECT` to its subscribers after every connect; the door counts them, starting at 1 when the stream was already connected, and ignores the first). The caller reloads the project then; never after the close function ran. In Node (rule tests) `EventSource` needs `--experimental-eventsource`, which the `rules` Vitest project passes.
- **Errors:** every method throws a `BackendError` ([errors.ts](../../frontend/src/backend/errors.ts)) with `kind`, `status`, `message` and, for `invalid`, `fields`. What the UI does for each kind:

| `kind` | From | UI |
|---|---|---|
| `invalid` | 400 | show `message`; show `fields[name]` beside the field |
| `locked` | 429 (lockout, rate limit) | show `message` (it says when to retry) |
| `forbidden` | 401, 403 (not verified, blocked, lockdown, not allowed) | show `message`; for an unverified account the verify gate text |
| `not-found` | 404 (also a wrong, disabled or unknown join code, an unknown invitee) | show `message`; never say more than the server did |
| `conflict` | 409 (invite already answered; a content save still refused after 20 tries, message `TOO_BUSY`) | show `message`; reload the list, or for a content save let the person try again |
| `unreachable` | no answer | "The server cannot be reached." and keep what is on screen |
| `unknown` | anything else | show `message` |

- **Tests:** unit tests beside the code (`errors.test.ts`, `mappers.test.ts`, `teams.test.ts`, `auth.test.ts`, fake `pb` objects); the chain door, routes and rules in `tests/rules/backend-door.rules.test.ts`, and for projects and content (concurrent saves, outsiders, live events) in `tests/rules/content-door.rules.test.ts`.

## Open choices (`1794370200_open_choices.js`)

A choice is a `connections` record whose `to_node` may be empty (editor cards plan). The migration:

- makes `to_node` optional and **removes its cascade delete**: purging a target node (Plan 7) leaves an empty choice instead of deleting the player's text. (`nodes.rules.test.ts` pins this.)
- makes the unique pair index partial, `WHERE to_node != ''`, so a node may have many empty choices but one choice per target.
- opens the create and update rules to an empty `to_node`, and lets an update change `to_node` to a node of the record's **own** project (`@request.body.to_node.project = project`). `from_node` and `project` still cannot change, and no rule becomes public.

The down step deletes the empty choices and restores the old field, index and rules. `1794370100_nodes_lines_connections.js` is never edited. The `created` time is the server's: PocketBase ignores one sent by the client, which is why a choice made again after an undo is listed last after a reload.
